# T1 本机核心交接 v2（R1 返工）

日期：2026-10-06。基线：v0.2-contract-2；任务 t1-core-runtime。此记录区分已实现底座与尚待 T2–T5 集成的产品功能，独立验收由 Manager 完成。

## 实现与环境

- 项目内 CPython 3.13.16 x64，实测 SQLite 3.53.1；启动/数据库连接拒绝低于 3.51.3 的 SQLite。固定解释器来源和摘要在 `runtime-win.json`，所有 25 个依赖版本及 Windows CPython 3.13 wheel SHA256 在 `requirements-win.lock`。
- `scripts/install.ps1` 校验下载摘要、解压路径、venv 位置、Python/SQLite 版本，再以 require-hashes 安装依赖；已完成首次等价步骤安装及脚本重复安装、pip check。未改全局 Python/PATH、注册表、服务或定时器。
- `scripts/scout.ps1` 包装 `python -I -m fashion_scout.launcher`。默认数据根为 LocalAppData/FashionScout，支持绝对 `--data-root`；根下 app.json 可配置绝对 media_root，媒体路径使用 root_id 加相对路径保存。
- Web/Worker 为两个独立进程；参数数组、shell=False、文件日志、独立进程组，优先请求退出宿主 Job。身份使用实际解释器 PID、创建时间、解释器路径和完整命令行核验，兼容 Windows venv 的中间启动进程。PID 文件中的数字本身不构成所有权证据。
- 本地 127.0.0.1 健康接口；启动器以随机 challenge/HMAC、instance、PID/birth 核对端口，凭据不放 runtime.json 或 stdout。key 文件沿用本地目录 ACL；当前没有浏览器写操作或业务 API，后续 T3 必须实现对应鉴权。
- 启动器写持久 starting_role 意图；中途退出后可核验已有握手再接管。若意图存在但握手缺失，返回 STARTUP_RECOVERY_REQUIRED，不猜测所有权或重复启动。stop 仅对核验过的实例写停止标记，等安全边界退出，超时明确 STOP_TIMEOUT，不强杀。

解释器来自 [Astral python-build-standalone 20261003](https://github.com/astral-sh/python-build-standalone/releases/tag/20261003)，发行使用方式见 [维护方文档](https://gregoryszorc.com/docs/python-build-standalone/main/running.html)。SQLite 门槛来自 [官方 WAL 文档](https://sqlite.org/wal.html) 的 WAL-reset 修复说明。

| Runs.create/default_plan/save_default/get/by_request | 仅显式 create 接受手动 Run；request_key 同参数幂等、不同参数冲突。活动 Run 单一唯一索引；新 key 遇活动任务复用并报告 ignored_overrides。默认方案 revision CAS；Run 冻结方案、UTC 窗口、站点入口/适配版本、基线状态。 |
| Runs.register_worker/claim/heartbeat/fence | DB 原子认领，owner+epoch+lease 检查。默认心跳 10 秒、lease 60 秒。过期且原进程确认死亡才恢复；单凭过期不能抢占活进程。所有 Worker 状态写入调用 fence。 |
| Runs.cancel/retry/recover_expired/release/finish | cancel/retry 操作 key 幂等；取消禁止新 item，但允许当前归档安全落地。失败/部分/取消可显式重试同一 Run；保留快照、已完成结果、人工状态和尝试历史。恢复递增 epoch，过期 owner 不能提交。success 必须覆盖完整、required 完整且所有已建 work item 完成；partial 必须 valid_results>0。 |
| Runs.ensure_item/start_item/complete_item/fail_item | (run_id,item_key) 唯一；完成项重复启动返回 False。错误写安全 code，失败后以 Run retry 重排队；网络内部最多 3 次请求策略由 T2 根据冻结快照实现，不能把 item 尝试历史当网络重试器。 |
| Archive.stage/commit/recover | T1 只处理已由调用方准备的字节。先 journal，校验字节/hash，fsync，硬链接不可覆盖发布，再在同一 DB 事务写 assets/item/journal。正式文件出现但 DB 未提交可重放；旧 lease 无权更新 DB；已完成输出不可替换。003 增加受 epoch 保护的 repair disposition/generation 与追加事件，详见下节。必须使用支持硬链接的本地卷且 temp/final 同 media root。 |
| Worker(paths, stopped, executor) / Context.checkpoint | T2 通过显式 Python executor 依赖注入接入，无 CLI 假成功/模拟站点开关。执行器按安全边界 checkpoint，返回真实 Outcome。当前默认 executor 明确 ADAPTER_NOT_IMPLEMENTED，绝不将空壳当成功。 |

002 迁移保留商品、观察、版本、媒体关系、收藏/已看、coverage、导出快照和维护表。它们不代表这些服务已经实现。人工状态与采集观察分表；T2/T3 必须保留这一区分。后续加表/改字段新增迁移，不能改已应用的 001/002；T1 校验会拒绝摘要变化。

## R1：journal 局部修复接口（T2 必须遵守）

原 v1 的 Worker 遇任一归档恢复失败就在 executor 前退出，导致失效暂存文件无法重取。v2 以新增 003 迁移修复，001/002 内容及摘要不变；已有 v2 数据库可原位升级。

`Context.archive_recovery` 提供本次恢复快照：recovered（journal ID）、failures（全部错误）、retryable、blocked、fatal_failures。错误条目含 journal_id、item_id、code、scope、action、evidence_ref；该快照不是修复后的实时查询。executor 可用 Archive.recover 再核验，持久权威是 journal、work_items 和 archive_journal_events。

| 情况 | 持久状态与执行责任 |
| --- | --- |
| 正式文件尚未发布，暂存文件缺失/字节或 hash 损坏 | journal failed/retryable，code=ARCHIVE_STAGING_UNAVAILABLE，work item pending。不阻止 executor。T2 用同一 item 调 start_item，按原快照重取并验证字节，再 stage/commit；不必创建新 Run。 |
| 未完成 journal 对应的正式目标已存在但内容冲突、资产元数据冲突 | blocked，scope=item，action=reconcile。不覆盖目标，不允许以另一个路径绕过该 intent；executor 可继续其他项。需要显式核验现场，修复后 recover 重新校验目标。 |
| 根目录不一致/不可用、权限或其他文件系统 I/O 故障 | blocked，scope=run，fatal_failures 非空。Worker 在 executor 前停止，保存安全错误 code 和证据；不能当作普通下载重试。DB 错误原样上抛，不在恢复中吞掉或重跑事务。 |

重新 stage 只接纳 retryable 且未发布、无已登记资产的旧意图，保留旧路径/hash/错误到追加事件。相同 hash 复用逻辑 journal 并递增 generation；不同 hash 创建新 journal、旧 intent 为 superseded。superseded 不再恢复；旧 epoch 拒写，旧 generation 不能在并发发布后提交新记录。重复 recovery 不复制相同错误事件；重复 stage/commit 不复制资产。既有尝试记录中的失败或中断不被恢复提交改写为成功。

executor 必须准确返回有效业务结果数与覆盖证据。Runs.finish 还会检查所有未提交且未被 superseded 的 journal：存在未解决项时，valid_results=0 强制 failed，>0 强制 partial，required_complete=false，并保留已有系统错误 code 或使用 ARCHIVE_REPAIR_PENDING。不能通过漏报某个 item 或误报完整覆盖获得 succeeded。普通重试保留同一 Run/快照、已完成资产与人工状态；修复失败不会阻止其他可继续的 item。

T2 仍负责网络限制、图片解码/格式/尺寸验证、内容变化、发现覆盖及商品版本关联；T3 负责产品/API、分页快照、已看语义、默认方案页面；T4 必须等待 T3 实际 API 后集成 Skill；T5 必须等待 T2 实际归档后集成导出。T1 的最小 health.py 可由 T3 合入 Web，需保留启动身份与健康契约。P0 三份设计文档保持既有验收版本，实施状态以 README 和本记录为准。

## 验证

项目内运行：

```powershell
.\scripts\install.ps1
.\.venv\Scripts\python.exe -m pytest tests/core -q --basetemp .runtime/pytest-r1-final --junitxml docs/verification/T1-R1-tests.xml
.\.venv\Scripts\python.exe -m pip check
git diff --check
```

核心测试覆盖：24 个并发创建请求只产生一个活动 Run，12 个并发认领只得到一个 lease；默认参数 CAS、请求冲突、terminal key 重放；SQLite 迁移/WAL/版本门槛/有限锁等待；取消/重试与人工收藏/类别/已看保留；旧 epoch 拒写、活进程 lease 过期不抢占；归档发布前/发布后/DB 提交失败恢复、损坏正式文件不覆盖、路径逃逸拒绝。

Windows 集成测试以真实子进程运行：父启动进程退出后另一进程查询仍可用；ensure 复用同 PID；未创建业务 Run；陌生端口进程不被操作；被篡改进程描述拒绝停止；真实 kill 测试 Worker 后保留同一 Run、已归档字节、人工状态，并拒绝旧 epoch；安全 stop；启动中断握手接管/缺证据阻断。合成 executor 仅存在 tests/core/process_helper.py，不访问站点，不作为生产成功路径。

首轮测试发现并修复 Windows venv 中间进程身份和只读文件句柄 fsync 不兼容两处问题。原 v1 的 28 项结果保留于 T1-tests.xml、T1-tests.txt；v2 当前验证为 39 项（含原 28 项与新增 11 项 R1 回归），原始输出/JUnit 在 T1-R1-tests.txt、T1-R1-tests.xml，环境与源文件摘要在 T1-R1-evidence.json。

新增回归以真实 Worker、SQLite 和文件验证缺失/损坏暂存重取（同 hash 与变化 hash）、正常项局部继续、旧 epoch/restage 幂等、已完成资产及人工状态/尝试历史保留、两次重试均进入 executor、0 有效结果 failed / 部分有效结果 partial、正式目标冲突、根目录错误、repair 事务失败回滚和 v2→v3 迁移。权限错误通过单个文件打开操作注入，未改本机 ACL；executor 与数据库未 mock，未访问真实站点。

39 项全套通过后补充了最终状态保留系统错误 code 的细节；受影响的 Run 与 Worker 修复测试再跑 26 项全通过，记录在 T1-R1-targeted.txt/xml。其余 13 项对应实现未变。已 committed 资产后续损坏的定期核查不属于本次 journal 恢复范围。

## 尚未证明的边界

- 实测为启动父进程退出后存活，并非关闭整个 Codex 应用/系统注销/重启实验。job_breakaway_requested 记录实际创建分支；宿主拒绝 breakaway 时退化运行，不能据此承诺关闭宿主后存活。
- 进程 kill、归档断点及 SQLite 事务中断已测；没有真实断电、磁盘硬件故障、Windows 休眠/唤醒实验，文件系统电源故障持久性仍待专项验收。
- 缺少启动握手的异常明确阻断并需核验现场；不能删除标记后盲启。T1 没有自动修复未知进程、自动重启 watchdog 或系统服务。
- 没有真实 Futario 请求、媒体下载、图片解析、业务 HTTP API、UI、Skill 客户端或 ZIP 导出。T1 测试通过不等于产品 A01–A13 全部验收。
- 依赖固定 Windows x64 CPython 3.13 wheel；未宣称 Linux/macOS、ARM、网络盘或任意用户自装解释器可用。
